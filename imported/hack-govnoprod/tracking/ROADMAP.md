# Дорожная карта: улучшение и развитие расширения и сопутствующего сервиса

Ниже — развёрнутый роадмап развития проекта (браузерное расширение + VS Code + backend-сервис). В начале расположены **задачи с наибольшей ценностью при минимальных усилиях**. Документ написан по-русски и охватывает функциональные требования, архитектуру, фичи безопасности/комплаенс, интеграции с LLM-провайдерами и метрики.

---

## Краткое резюме и приоритеты

- Цель: сделать расширение + сервис, которые снижают количество дорогостоящих/опасных LLM-запросов, автоматически улучшают промпты, предотвращают утечки PII/корпоративных данных, и предоставляют корпоративным администраторам политики контроля.
- Основные пользователи: отдельные пользователи, команды, и корпорации (enterprise deployment).
- Базовый стек рекомендаций: TypeScript, React (popup/webview), Vite, MV3 для браузера, VS Code extension API + React webview, бэкенд на Node.js/TypeScript (Fastify/Express/Nest), PostgreSQL для хранения политик + Redis для кэша/очередей. Подключение к LLM реализуется через слой адаптеров (OpenAI, Anthropic, AzureOpenAI и т.п.).

### Быстрые задачи (высокая ценность, низкие усилия)
1. Автоматическое улучшение выделенного промпта в `textarea` (функция "Apply safe patches" — фронтенд + вызов `/analyze/apply`).
2. Кнопка «Export analysis» (Markdown/JSON) — локальный экспорт и вызов `/analyze/export`.
3. Поток уточняющих вопросов: показать вопросы из `/analyze`, получить ответы от пользователя и вызвать `/analyze/clarify`.
4. Перехват отправки формы и локальная подсказка улучшений (клиентский хук и неблокирующая подсказка).
5. Добавить базовые детекторы PII (email, телефон, номера карт и т.п.) и интерфейс для редактирования шаблонов/паттернов в UI (не требует LLM).

## Полный роадмап (фазы)

Каждая фаза включает: цель, задачи, оценки (низкая/средняя/высокая), необходимые компоненты и критерии приёмки.

### Фаза 0 — Подготовка инфраструктуры (1–2 недели)
- Цель: унифицировать репозиторий и базовые контракты API.
- Задачи:
  - Определить и задокументировать OpenAPI/REST контракт для `/analyze`, `/analyze/apply`, `/analyze/clarify`, `/analyze/export`.
  - Создать слой адаптеров для LLM-провайдеров (интерфейсы + первичный адаптер для OpenAI).
  - Добавить таблицы в БД: `policies`, `users`, `org_settings`, `audit_logs`.
- Оценка: низкая
- Критерии приёмки:
  - OpenAPI-спецификация доступна, мок-сервер отвечает на ранние версии эндпоинтов.
  - CI проверяет сборку бэкенда и расширений.


### Фаза 1 — Базовый UX и безопасность (2–4 недели)
- Цель: реализовать основные пользовательские сценарии и базовую защиту PII.
- Задачи:
  1. Реализовать поток выделения текста и вызова `/analyze` из всплывающего меню (content.ts → background.ts → бэкенд).
  2. Реализовать функцию «Apply safe patches» — вызов `/analyze/apply?apply_safe_all=true` и безопасная замена текста в целевом `textarea`.
  3. Отображать список патчей и уточняющих вопросов в всплывающем окне/модальном диалоге (React + Tailwind).
  4. Добавить экспорт анализа в Markdown/JSON локально и через `/analyze/export`.
  5. Добавить локальные детекторы PII (на основе regex) и интегрировать их как preliminary blocks в результат `/analyze`. Это позволит блокировать загрузку файлов с совпадениями (см. Фазу 2).
- Оценка: средняя
- Критерии приёмки:
  - Пользователь может выделить текст и получить список патчей.
  - Функция Apply safe patches безопасно заменяет текст в `textarea` без перезагрузки страницы.
  - Экспорт генерирует валидный Markdown/JSON и содержит результаты и применённые патчи.


### Фаза 2 — Перехват файлов и блокировка загрузки (3–5 недель)
- Цель: предотвращать загрузку файлов, содержащих PII или корпоративные данные, и предоставить удобный UX для разрешений.
- Задачи:
  1. Content script: прослушивание событий `submit`/`fetch`/`XMLHttpRequest`/`form` и интеграция с DOM-полями загрузки файлов для анализа перед отправкой.
  2. Анализ содержимого файлов на стороне расширения (локальный парсер): текстовые файлы, PDF, DOCX, изображения (OCR — опционально).
  3. Если файл содержит совпадения с политикой, блокировать отправку и показать модальное окно с объяснением и опциями (локальная редакция / отмена / отправить с указанием обоснования и логированием).
  4. Настраиваемые паттерны перехвата в `policies` (regex, allowlist/denylist). Политики применяются по сайту и по организации.
- Оценка: высокая
- Критерии приёмки:
  - Расширение перехватывает загрузки и блокирует отправку при совпадении с политикой.
  - Администратор может задать и обновить паттерны; изменения вступают в силу за согласованный интервал.


### Фаза 3 — Корпоративные функции и политики (4–6 недель)
- Цель: сделать сервис пригодным для корпоративного использования.
- Задачи:
  1. Multi-tenant: учётные записи организаций, политики per-org, роли (админ/пользователь), уровни применения (warn/block/auto-redact).
  2. Аудит: логирование попыток отправки prompt, результатов анализа, применённых патчей и обоснований в `audit_logs`.
  3. Панель администратора: управление политиками, шаблонами, allowlist/denylist сайтов и режимами применения.
  4. Развёртывание: варианты для корпоративного развёртывания — управляемое расширение и централизованная синхронизация политик (через защищённый endpoint или S3-конфиги).
- Оценка: высокая
- Критерии приёмки:
  - Администратор может создавать и развертывать организационные политики на клиентах.
  - Аудит-логи полноценно сохраняются и доступны для экспорта/анализа.


### Фаза 4 — Переписывание промптов и рекомендации под конкретные LLM (3–6 недель)
- Цель: давать рекомендации под конкретные LLM согласно гайдлайнам провайдера и переписывать промпты для экономии токенов и снижения галлюцинаций.
- Задачи:
  1. Модуль оптимизации промптов: правила + опциональная небольшая локальная модель для перефразирования.
  2. Провайдеро-специфические шаблоны и руководства: OpenAI, Anthropic, Azure, Llama2, Claude.


### Детализация функций и шаги реализации (по пунктам)

1) Экспорт анализа и метаданные
- API:
  - POST `/analyze/export` тело: { analysis_id: string, format: 'json'|'md', include_redactions: bool }
  - Ответ: { download_url?, payload }
- Интерфейс:
  - Модальное окно экспорта: чекбоксы включения редакции, диффов, метаданных аудита.
- Шаги:
  - Обновить сериализатор бэкенда.
  - Добавить endpoint для скачивания + подписанные URL для корпоративных клиентов.
  - Добавить модал и сохранение файла на клиента.

2) Apply safe patches: превью, выбор, отмена
- Модель данных: Patch { id, score, description, diffs }
- Клиент:
  - Реализовать оптимистичное применение патчей с буфером транзакций.
  - Undo: хранить предыдущие значения в памяти в рамках сессии.
- Шаги:
  - Расширить `/analyze/apply` для возврата атомарных патчей.
  - Добавить модальное окно с превью патчей.

3) Перехват файлов и локальный парсинг
- Изначально поддерживаемые форматы: txt, pdf, docx, csv
- Библиотеки: pdf.js (в браузере), mammoth.js (docx), встроенный FileReader
- Шаги:
  - Привязать перехват к полям загрузки файлов и событию submit формы.
  - Извлекать текст и запускать локальные regex-детекторы.
  - При совпадении показывать модальное окно с опциями редактирования/редакции.

4) Политики: CRUD + синхронизация + применение
- Пример JSON политики (технические ключи сохранены для совместимости):
```json
{
  "id": "policy-1",
  "org_id": "org-123",
  "name": "Default PII policy",
  "rules": [
    {"id":"r1","type":"regex","pattern":"\\b\\d{3}-\\d{2}-\\d{4}\\b","action":"block","severity":"high"},
    {"id":"r2","type":"keyword","keywords":["confidential","secret"],"action":"warn","severity":"med"}
  ],
  "enforcement": {"default":"warn","site_exceptions":[]},
  "version": 3,
  "updated_at": "2025-08-01T12:00:00Z"
}
```
- Шаги:
  - Бэкенд: реализовать CRUD для `/policies`.
  - Клиент: логика синхронизации с проверкой версии/etag.
  - Критерий: изменения политики распространяются в оговоренный интервал.

5) Метрики энтропии и неопределённости
- Метрики для вычисления:
  - `token_entropy` (энтропия Шеннона по распределению токенов)
  - `ambiguous_terms_ratio` (доля неоднозначных терминов)
  - `missing_instructions_ratio` (эвристическая оценка отсутствующих инструкций)
- Шаги:
  - Реализовать модуль метрик в сервисе анализа на бэкенде.
  - Возвращать `entropy_score` в ответе `/analyze`.
  - UI: отображать бейдж и предупреждения при превышении порогов.

6) Рекомендации под конкретного провайдера
- Для каждого провайдера хранить `provider_guides/{openai,anthropic,azure}.json`.
- Руководства включают: рекомендуемые системные сообщения, значения temperature, max tokens, шаблоны ролей.
- Шаги:
  - Реализовать адаптер провайдера.
  - Показывать рекомендации в UI с оценкой экономии токенов.

7) Интеграция с VS Code
- Возможности:
  - Команда для сканирования рабочего пространства.
  - Аннотации в файлах/PR.
  - Временная шкала энтропии по файлу.
- Шаги:
  - Реализовать фоновой анализатор в `extension.ts`.
  - UI во webview: график (chart.js / recharts).
  - Git-интеграция: сопоставление изменений файлов с коммитами через `git log -p`.

8) Панель администратора и отчётность
- Отчёты:
  - заблокированные загрузки в день;
  - промпты с высокой энтропией по пользователям;
  - оценённая экономия токенов.
- Шаги:
  - Построить админ-панель (React) в `apps/admin` или расширить popup с админ-маршрутами.
  - Бэкенд: endpoints для отчётов `/reports/usage`, `/reports/compliance`.

9) Аудит-логи и соответствие требованиям
- Данные для логирования: timestamp, user, org, action, resource, matched_rules, decision.
- Хранение: настраиваемое по организации.
- Шаги:
  - Создать таблицу `audit_logs`.
  - Возможность стримить логи в S3 и экспорт через админ-интерфейс.

10) Тестирование и бенчмарки
- Создать корпус тестовых данных: примеры промптов, файлы, кейсы на границе допустимого.
- Тесты:
  - unit-тесты для детекторов;
  - интеграционные тесты для `/analyze`-флоу;
  - e2e-тесты для браузерного расширения (puppeteer/playwright).

## Примеры контрактов API (микросниппеты)

- `/analyze` (POST)
Запрос:
```json
{
  "text": "...",
  "context": {"url":"...","site":"example.com"},
  "user_id": "...",
  "org_id": "...",
  "provider": "openai"
}
```
Ответ:
```json
{
  "analysis_id": "a-123",
  "patches": [{"id":"p1","desc":"shorten intro","diff":"-...+..."}],
  "questions": [ {"id":"q1","text":"What is the target audience?"} ],
  "entropy_score": 0.72,
  "matched_policies": ["r1","r2"]
}
```

- `/analyze/apply` (POST)
Запрос: { analysis_id: string, selected_patch_ids: string[] }
Ответ: { improved_prompt: string, applied_patch_ids: [], token_delta: -12 }

## Примеры политик и режимы применения

- Режимы применения:
  - `warn`: показывать предупреждение, но разрешить отправку;
  - `block`: блокировать отправку/загрузку;
  - `auto_redact`: автоматически редактировать (редактировать) чувствительные фрагменты перед отправкой.

- Гранулярность политики:
  - по сайту, по пользователю, по организации, глобальный дефолт.

## Операционные заметки: развёртывание и приватность

- Для корпоративных клиентов предоставить варианты: облачное hosted и on-premise развёртывание.
- Синхронизацию политик выполнять через защищённый канал (подписанные конфиги) и проверять подпись на клиенте.
- Секреты: хранить ключи провайдеров в secret-manager; не сохранять необработанные промпты в логах без явного согласия.
